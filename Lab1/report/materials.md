# Материалы для отчёта по лабораторной работе

ИПС «Арахна» — информационно-поисковая система по документам локальной
вычислительной сети. Вариант 3: элементы ИИ — интерфейс с пользователем;
сфера применения — ЛВС; стратегия поиска — векторная; язык — русский.

---

## 2. Структура базы данных

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `documents` | документы, собранные пауком | `id`, `path`, `uri`, `host`, `title`, `text`, `ext`, `mtime`, `date_added`, `content_hash`, `term_count`, `vector_norm` |
| `terms` | словарь системы | `id`, `lemma`, `df` (= P_i) |
| `postings` | инвертированный индекс | `term_id`, `doc_id`, `tf` (= Q_ij), `weight` (= A_ij) |
| `forms` | словоформа → лемма | `form`, `term_id`, `freq` |
| `sources` | ресурсы ЛВС для обхода | `root_path`, `kind` (local/unc), `label`, `enabled`, `last_crawl` |
| `crawl_log` | журнал обходов | `started_at`, `added`, `updated`, `skipped`, `removed`, `errors` |
| `query_log` | история запросов | `raw_query`, `normalized`, `ts`, `results_count`, `took_ms` |
| `feedback` | отметки релевантности пользователя | `query`, `doc_id`, `mark` (±1) |
| `eval_queries` | эталонные информационные потребности | `id`, `text`, `note` |
| `qrels` | эталонная разметка релевантности | `query_id`, `doc_id`, `rel` (0/1/2) |
| `achievements`, `settings` | служебные | — |

Связи: `postings.term_id → terms.id`, `postings.doc_id → documents.id`,
`forms.term_id → terms.id`, `qrels.query_id → eval_queries.id`,
`qrels.doc_id → documents.id` (каскадное удаление).
Индексы: `postings(term_id)`, `postings(doc_id)`, `terms(lemma)`, `forms(form)`,
`documents(host)`.

Хранение весов A_ij прямо в `postings` позволяет выполнять поиск одним запросом
к индексу, не обращаясь к текстам документов; тексты нужны только для сниппетов.

## 3. Основные алгоритмы

### 3.1. Обход ЛВС (агент)

1. Для каждого включённого ресурса — рекурсивный обход с пропуском служебных
   каталогов и файлов неподдерживаемых форматов.
2. Для каждого файла сравниваются `mtime` и размер с сохранёнными в базе:
   совпали — файл не читается (инкрементальность).
3. Изменившиеся файлы читаются в пуле потоков (задача ввода-вывода),
   считается `sha1`; если хеш не изменился, обновляется только `mtime`.
4. Ошибки доступа и повреждённые файлы записываются в журнал, обход не
   прерывается.
5. Документы, файлы которых исчезли из ЛВС, удаляются из базы.

### 3.2. Индексирование

```
для каждого документа j:
    текст → токены → стоп-слова отброшены → леммы
    Q_ij ← частота леммы i в документе j
    P_i  ← число документов, содержащих лемму i
для каждой леммы i:      B_i  = log( N / P_i )                (1.5)
для каждой пары (i, j):  A_ij = Q_ij · B_i                    (1.6)
для каждого документа j: ‖D_j‖ = sqrt( Σ_i A_ij² )
```

Индекс перестраивается целиком: добавление документов меняет N, а значит и все
инверсные частоты. Для коллекции из 72 документов перестройка занимает ≈ 0,2 с.

### 3.3. Поиск (векторная модель)

```
запрос → леммы                        w_qj = 1
        + синонимы, исправления       w_qj = 0,5
выбрать из индекса строки с леммами запроса
для каждого документа:  (D,Q) = Σ_i A_ij · w_qi
                        rank  = (D,Q) / ( ‖D‖ · ‖Q‖ )
фильтры: «все слова обязательны», диапазон дат
сортировка по убыванию rank, сниппет 300 символов с подсветкой
```

### 3.4. Обратная связь по релевантности (Рокчио)

```
Q' = α·Q + β/|Dr| · Σ_{d∈Dr} d/‖d‖ − γ/|Dnr| · Σ_{d∈Dnr} d/‖d‖
α = 1,0   β = 0,75   γ = 0,15
отрицательные компоненты обнуляются, вектор усекается до 40 терминов
```

### 3.5. Исправление опечаток

Слово, отсутствующее в словаре системы, сравнивается со словоформами индекса по
расстоянию Дамерау — Левенштейна (порог 1 для слов до 5 букв, иначе 2). Из
кандидатов выбирается ближайший, при равенстве — более частотный.

## 7. Анализ полученных данных и предложения по улучшению

**Что показывают цифры.**

1. **Высокая полнота при низкой точности по всей выдаче.** Полнота 0,92 и
   точность 0,34 — прямое следствие векторной модели: документ попадает в
   выдачу, если содержит хотя бы одно слово запроса. При этом P@5 = 0,54 и
   MAP = 0,70 показывают, что релевантные документы стоят в начале списка —
   то есть ранжирование работает, а «хвост» выдачи просто длинный.
2. **Морфология даёт +13 % к MAP** (0,618 → 0,700). Без лемматизации запрос
   «локальных сетей» не находит документ со словами «локальная сеть» — для
   русского языка это критично.
3. **Расширение синонимами даёт ещё +7 %** (0,700 → 0,750) и заметный прирост
   R-точности (0,593 → 0,658): тезаурус связывает «коммутатор» со «свитчем»,
   «резервный» с «бэкапом». Пониженный вес 0,5 у добавленных терминов не даёт
   им перебивать слова, введённые пользователем.
4. **Строгий режим резко ухудшает MAP** (0,303). Требование присутствия всех
   слов отсекает документы, где одно из слов запроса выражено синонимом; для
   естественно-языковых запросов из 4–6 слов режим почти бесполезен и оставлен
   только как явно включаемая опция.
5. **Худшие запросы — с межтематической омонимией.** «Запросы SQL к базе
   данных» (AP = 0,399) и «инвертированный индекс поисковой системы»
   (AP = 0,442): слова «запрос», «индекс», «база» частотны и в разделе о СУБД,
   и в разделе об информационном поиске. Схожая картина у «морфологический
   анализ русского языка» (AP = 0,467) — слово «анализ» размывает выдачу.

**Предложения по улучшению СИП.**

* **Учитывать позицию термина**: увеличивать вес слов из заголовка и первого
  абзаца — заголовок точнее отражает тему, чем случайное упоминание в тексте.
* **Учитывать длину документа** (BM25 вместо чистого TF-IDF): нормировка по
  средней длине документа устойчивее евклидовой при разбросе объёмов.
* **Учитывать соседство слов**: повышать ранг документов, где слова запроса
  стоят рядом, — это напрямую лечит проблему омонимии «индекс СУБД» против
  «инвертированный индекс».
* **Взвешивать синонимы по надёжности** и расширять тезаурус автоматически —
  по совместной встречаемости терминов в коллекции.
* **Отсекать хвост выдачи** по порогу ранга или по резкому падению
  относительно первого результата: это поднимет точность, почти не задев
  полноту в первых десяти позициях.
* **Накапливать обратную связь между сессиями**: сейчас отметки Рокчио
  привязаны к конкретному тексту запроса; их обобщение по леммам дало бы
  эффект и для похожих запросов.
* **Расширить эталон**: 20 запросов и 155 оценок достаточно для лабораторной,
  но для устойчивых выводов нужен пул из нескольких сотен оценок.
